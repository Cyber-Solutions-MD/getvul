1. A short intro paragraph: `/ready` (Postgres SELECT 1 + Redis PING, 500ms bound each) is the readiness gate; the docker-compose backend healthcheck (interval 5s) is the de-facto active monitor for this single-VM topology. Failure detection = (a) `/ready` returns 503 with a per-dependency body, and (b) the backend emits a structured `readiness_check_failed` log line (level ERROR) naming which dependency failed.

2. A symptom -> /ready state -> log event -> operator action table with at least these rows:
   | Symptom | `/ready` body | Log event | Operator action |
   - Postgres unreachable/down: `503` `{"postgres":{"ok":false,...},"redis":{"ok":true,...}}`; event `readiness_check_failed` (`postgres_ok=false`); action = check Postgres container/health (`docker compose ps`, `pg_isready`), inspect connection/pool exhaustion, restart DB or scale pool; compose restarts the backend once /ready recovers.
   - Redis unreachable/down: `503` `{"redis":{"ok":false,...}}`; event `readiness_check_failed` (`redis_ok=false`); action = check Redis container, note the rate limiter fails-OPEN (traffic still flows) while OIDC state fails-CLOSED (new logins blocked) — restore Redis promptly; explain why the node still reports not-ready per the D-04 hard-fail policy.
   - Probe timeout (dep slow >500ms): `503` with `error:"timeout"`; same event; action = investigate dependency latency/saturation.

3. A subsection `### nginx upstream — single-VM limitation` documenting Pitfall 3 verbatim in intent: open-source nginx IGNORES `max_fails`/`fail_timeout` for a single-server upstream group, so passive ejection is INERT on this single-backend deployment. The `upstream backend` block is forward-compatible scaffolding (activates when a second backend is added). The ACTUAL readiness gate here is the docker-compose healthcheck + container restart policy. Active `/ready` probing would require nginx Plus or an external HTTPS uptime monitor pointed at the public `/ready` endpoint — recommend wiring such a monitor to page on repeated 503.

4. A one-line note on the CI/dev asymmetry (RESEARCH Q2): `docker-compose.ci.yml` gates the frontend on `backend: condition: service_healthy`; `docker-compose.yml` (dev) intentionally leaves `depends_on` unconditioned to keep dev startup fast.
