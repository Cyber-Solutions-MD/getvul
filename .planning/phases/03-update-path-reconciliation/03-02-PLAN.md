       ## Rollback

       Rollback is re-deploying a prior release tag through the same CD workflow — there is no separate rollback script. Every rollback lands on a real, CI-gated release tag (never a hand-picked SHA).

       ### Step 1 — Identify the prior release tag

       ```bash
       gh release list --limit 5
       ```

       The newest entry is the current (bad) release; the next entry down is the prior good release. Or open the GitHub Releases page and note the previous version.

       ### Step 2 — Check whether the bad release ran a destructive migration

       > **WARNING — A CODE ROLLBACK DOES NOT REVERT DATABASE MIGRATIONS.**
       >
       > Rolling back via a git tag restores code only. If the bad release added an Alembic
       > migration that dropped a column or table, checking out the prior tag will NOT restore
       > that data — the prior code will fail or corrupt data when the schema no longer matches.
       > You must restore from a `pg_dump` backup taken before the failed deploy. If no backup
       > exists, the data may be unrecoverable. Contact your DBA before proceeding.
       >
       > If the migration was purely additive (added a column / created a table), a code rollback
       > is safe — the prior code simply ignores the new schema objects.
       >
       > Automated down-migrations and pre-deploy snapshots are out of scope for this phase (deferred to PROD-05 / backup policy).

       ### Step 3 — Trigger the CD workflow at the prior tag

       ```bash
       gh workflow run cd.yml --field release_tag=<prior-tag>   # e.g. v1.0.0
       ```

       Or: GitHub UI → Actions → "CD — Deploy to GCE" → Run workflow → enter the prior tag in `release_tag`.

       The CD job SSHes to the VM, runs `git fetch --tags --force && git checkout --force <prior-tag>`, rebuilds, and health-checks — the identical path a normal release deploy takes.

       ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator (workflow_dispatch input) → CD runner → VM | The `release_tag` input flows into `git checkout` inside an SSH heredoc executed on the GCE VM as the `deploy` user — untrusted operator input crosses into a shell command on production |
| GitHub release event → CD runner | `github.event.release.tag_name` is set by GitHub from the published release; trusted, but must not be confused with the empty `inputs` context on that trigger |
| Remote git tags → VM working tree | A moved/re-tagged release could point the checkout at an unexpected commit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04 | Tampering | `release_tag` workflow_dispatch input injected into `git checkout "$DEPLOY_TAG"` inside the SSH heredoc | mitigate | Task 1: `set -e` in the heredoc; the empty-string guard step exits 1 before any SSH if no tag resolved; `git checkout` rejects any ref it cannot resolve (a bad/injected value fails fast with a clear pathspec error, not arbitrary execution). The value is a single positional arg to `git checkout`, not eval'd. Residual risk LOW: only operators with Actions run-workflow permission can dispatch. Optional future hardening noted (`git ls-remote --tags origin "$DEPLOY_TAG"` pre-check) — deferred, not required for L1. |
| T-03-05 | Tampering | Stale/moved local tag on the VM causes checkout of the wrong commit | mitigate | Task 1: `git fetch --tags --force` updates re-created/moved tag refs before checkout (git ≥2.20 requires `--force` to update tags) — the VM always resolves the tag to the remote's current commit |
| T-03-06 | Tampering / Elevation | `github.ref_name` used as the deploy ref would silently deploy `main` HEAD on a manual dispatch | mitigate | Task 1 uses `github.event.release.tag_name || inputs.release_tag` and explicitly forbids `github.ref_name` (acceptance criterion: `grep -c "github.ref_name" cd.yml` → 0) |
| T-03-07 | Information Disclosure | Operator assumes a code rollback also reverts the DB and loses data on a destructive migration | mitigate | Task 2: prominent WARNING blockquote placed BEFORE the trigger step in the runbook (D-08, research §Pitfall 5) |

No HIGH-severity unmitigated threat remains. The dispatch-input injection (T-03-04) is bounded to Actions-authorized operators and constrained to a `git checkout` pathspec that fails closed under `set -e`.
</threat_model>
