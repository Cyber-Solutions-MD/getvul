## Design System

| Property | Value |
|----------|-------|

**Already installed shadcn primitives** (reuse, do not reinstall): `button`, `card`, `dropdown-menu`, `form`, `input`, `label`, `progress`, `textarea`, `tooltip`.

**Already installed project primitives** (reuse verbatim): `ConfirmModal`, `ResponsiveDialog` (desktop dialog / mobile vaul bottom-sheet), `Badge`, `ChipBar`, `EmptyState` (compound: Title/Body/Actions/Suggestion), `PartialFailureBanner`, `Pagination`, `Avatar`, `DrillPanel` (generalized `idKey`/`renderContent` slot — see D-D-02 in prior-phase decisions), `BlockedToggle` (inline reason-editor pattern), `reassign-combobox.tsx` (searchable tenant-user picker — this IS the approver-picker precedent, see below).

**No new shadcn components required this phase.** The codebase's established convention for `<select>` and date inputs is a **native, hand-styled element** (`sla-escalation-pane.tsx:653` uses a plain `<select>` with the shared `FIELD_CLASS`/`field-input` Tailwind treatment), not shadcn's Radix `select`/`popover`/`calendar`. This phase follows that precedent:
- **Scope-target picker** (asset-group dropdown) → native `<select>` styled with the existing `field-input` classes.
- **Expiry date** → native `<input type="date">` styled with the existing `field-input` classes, `min`/`max` attributes enforcing the future-only + hard-cap validation (D-14).
- **Approver** → reuse `reassign-combobox.tsx` verbatim as the pattern (searchable tenant-user list, avatar + name), not a native select — D-08 requires a real FK lookup, and this combobox already solves "pick one tenant user" elsewhere in the app.

## Typography

Reused verbatim from `foundation.md`'s 1.25 modular scale — exactly 4 sizes, exactly 2 weights, per this phase's needs:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`--text-sm`) | 400 regular | 1.5 (`--leading-base`) — justification text, table cell values, dialog helper text |
| Label | 12px (`--text-xs`) | 500 medium* | 1.3 (`--leading-snug`) — uppercase tracking-wide field labels ("Approver", "Expires"), table column headers, drill-panel `<h4>` section labels |
| Heading | 20px (`--text-xl`) | 600 semibold | 1.3 (`--leading-snug`) — dialog title ("Grant exception"), card/section titles |
| Display | 32px (`--text-3xl`) | 600 semibold | 1.1 (`--leading-tight`) — `/dashboard/exceptions` page title ("Exceptions") |

*Note: 500-medium is the existing label weight in this codebase (e.g. `sla-escalation-pane.tsx` labels use `font-medium`); together with 400 and 600 that is 3 weights in the raw type system, but this phase's own new copy only introduces two weight *roles* — **regular (400) for body/data, semibold (600) for headings/emphasis**. Field labels reuse the pre-existing 500-medium utility already present sitewide; it is not a new weight decision for this phase.

Tabular numerals (`font-variant-numeric: tabular-nums`) apply to the expiry "Nd left" countdown and the "granted N days ago" relative date — both are terminal-pasteable/scannable values per the mono-usage rule.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg` (`#0E0B1A` dark / `#FAF7F2` light) | Page background of `/dashboard/exceptions`, dialog backdrop |
| Secondary (30%) | `--color-surface` (`#1A1430` dark) | Exceptions table container, dialog panel body, drill-panel Actions-section card |
| Accent (10%) | `--color-violet` (`#A78BFA` dark / `#7C3AED` light) | Reserved for: focus rings on every form input (violet 3px halo, never the CTA's pink); the active state of the scope segmented-control ("This finding" / "This asset" / "Asset group"); the "View finding" cross-link from an exceptions-list row back to its source CVE |
| Destructive | `--color-danger` (`#F87171` dark / `#DC2626` light) | Reserved for: the Revoke button's icon/text on hover, and the Revoke `ConfirmModal`'s confirm button — no other element in this phase uses it |

Accent reserved for: focus rings, scope segmented-control active state, and the finding cross-link — **never** the primary submit action. "Grant exception" (the dialog's submit) uses the pre-existing sitewide `--gradient-sunset` CTA treatment (`btn-cta`, pink→violet→amber) — that gradient is a locked, already-shipped primitive reused here unchanged, not a new color decision for this phase.

**Type badge colors** (FALSE_POSITIVE / ACCEPTED_RISK) reuse the existing **status-pill family** (a color family deliberately distinct from severity, per `visual-language.md`) rather than inventing new hues:
- `FALSE_POSITIVE` → violet pill (`status-pill` "Open" hue) — "Not a real issue"
- `ACCEPTED_RISK` → amber pill (`status-pill` "In progress" hue) — "Known, tolerated"

**Expiry countdown** reuses the existing **SLA 3-tier pill** (`sla-pill`) treatment verbatim, restricted to its two non-overdue tiers (an active exception can never be "overdue" — compute-on-read means the moment it lapses it simply stops appearing):
- `sla-pill.soon` (amber) → `≤ 7d left` ("expiring soon")
- `sla-pill.ok` (green) → `> 7d left`

Revoked/expired historical rows (if the list surfaces past exceptions) get a neutral **muted chip** (`text-text-muted`, no color-coded urgency) reading "Revoked" or "Expired" — never reuse `sla-pill.overdue`'s red, since that specifically means "SLA breached," not "exception lifecycle ended."

## Layout & Entry Points

No new page-layout pattern is invented — this phase composes three already-validated patterns from `page-layouts.md` / `interaction-patterns.md`.

### 1. Grant entry point — vulnerability drill panel (existing surface, additive)

The vuln drill panel's existing **Actions** section (`drill-panel.tsx` → `DrillContent`, sibling to "Create ticket" / "Snooze 24h") gains two new secondary buttons:

```
Actions
┌──────────────────────────┐
│ [gradient] Create ticket │
│ [secondary] Snooze 24h   │
│ [secondary] Accept risk  │      <- new
│ [secondary] Mark false positive │  <- new
└──────────────────────────┘
```

Clicking either opens the **Exception Grant dialog** (new component) via `ResponsiveDialog` (desktop centered dialog / mobile vaul bottom-sheet — the established dual-surface pattern, same as `ConfirmModal`), with `type` pre-set (`ACCEPTED_RISK` / `FALSE_POSITIVE`) and scope pre-defaulted to **"This finding"** (the CVE × asset the drill panel is already showing).

### 2. Exception Grant dialog (new form — modal, not a full page per the "modals are for confirmations/short forms, not content that fits a panel" convention; this form is short enough — 4 fields — for a dialog)

```
┌─ Grant exception ─────────────────────────── × ─┐
│  [chip: Accept risk ▾]  CVE-2024-3094 on prod-db-01 │  <- type + fixed CVE/asset context, mono
│                                                    │
│  Scope                                             │
│  ( This finding ) ( This asset ) ( Asset group )   │  <- segmented control, violet active state
│  [if Asset group selected: native <select> of asset groups]│
│                                                     │
│  Approver *                                        │
│  [reassign-combobox: search teammates…]            │
│                                                     │
│  Justification *                                   │
│  [textarea, 4 rows, 1000 char cap, counter near limit] │
│                                                     │
│  Expires *                                         │
│  [native <input type=date>, min=tomorrow, max=cap] │
│  Mandatory — this decision resurfaces for review on this date. │
│                                                     │
│         [secondary] Cancel   [gradient] Grant exception │
└─────────────────────────────────────────────────────┘
```

Field order is fixed: Scope → Approver → Justification → Expiry (matches the requirement's own EXC-01 ordering: "scope, justification, approver, expiry" reordered slightly so the CVE/target context anchors the top and the date — the most consequence-bearing field — anchors the bottom just above the primary action, mirroring `blocked-toggle.tsx`'s label→input→save reading order).

Submit ("Grant exception") stays **disabled** until all four fields are filled (D-06: all four mandatory, no partial submit) — see UI Considerations below.

### 3. Exceptions list — `/dashboard/exceptions` (new page, reuses the list+chip-bar pattern from `page-layouts.md` §3)

```
Exceptions                                            (Display, 32px)

[chip-bar: search-target · Type: False positive/Accept risk · Scope: Finding/Asset/Asset group · Clear all]

┌ Type ┬ CVE / target ┬ Scope ┬ Approver ┬ Granted ┬ Expires ▾ ┬ ┐
│ pill │ mono         │ label │ avatar+name │ Nd ago │ sla-pill │ Revoke │
└──────┴──────────────┴───────┴──────────┴─────────┴──────────┴──┘
Showing 1–10 of N · pagination (mono, reuses existing `Pagination` component)
```

- No persistent left filter drawer (matches every other list route).
- No dialog-launching gradient CTA on this page's chrome — granting is contextual to a finding (see entry point 1), so this list is **manage-only** (view + revoke), consistent with a read/manage list not needing its own "create" affordance when creation is scoped elsewhere.
- **Expires** column header is clickable to toggle sort direction; **default sort = ascending (soonest-expiring first)** so "expiring soon" rows surface without needing a filter (D-19).
- Row click does **not** open a 420px drill panel (the record has only 4 short fields, no benefit to a side panel) — instead clicking a row's Approver/justification area reveals an inline expand (accordion) showing the full justification text + audit metadata (who granted, when), avoiding a redundant modal-inside-modal.
- Revoke is a per-row ghost/secondary button that opens the existing `ConfirmModal` (variant `"warning"`).

## UI Considerations

Applicable state considerations resolved: 13 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | grant-form (form) | ✅ covered | Dialog opens with type pre-selected from the triggering drill-panel button, scope defaulted to "This finding" (the originating CVE+asset), and Expires pre-filled to the type's default window (exact day-count is a planning decision, D-13) — the form is never blank on its consequential fields, but Expires stays editable and submit is still gated on all four fields being explicitly present. |
| empty | exceptions-list (list-collection) | ✅ covered | "No exceptions granted yet" heading + explanatory body + "View vulnerabilities" secondary action (see Copywriting Contract) — never granted case. |
| empty | exceptions-list filtered-to-zero (list-collection) | ✅ covered | "Nothing matches this filter" heading + body naming the active chip conjunction + gradient "Clear all filters" action, matching the documented vulnerabilities-list filtered-empty pattern. |
| loading | grant-form (form) | ✅ covered | Approver field renders disabled with placeholder "Loading approvers…" until the tenant-user list resolves; submit stays disabled until it does (single API request, <300ms typical — no skeleton needed per state-patterns.md's "simpler loading" rule). |
| loading | exceptions-list (list-collection) | ✅ covered | Skeleton table rows (shimmer, 6-8 rows) matching the sitewide `.skeleton`/`.skel-pill` treatment — never a blank screen. |
| error | grant-form (form) | ✅ covered | Four distinct error copy strings declared above: precondition (D-03), expiry-cap (D-14), approver-fetch, and generic submit failure — each surfaced at the right scope (dialog-level banner vs. field-level text), never a generic "Something went wrong." |
| error | exceptions-list (list-collection) | ✅ covered | Reuses `PartialFailureBanner` verbatim — amber, HTTP code + request ID + Retry now, per `state-patterns.md`'s error convention (not a full-page red error, data may still partially exist). |
| populated | exceptions-list (list-collection) | ✅ covered | Column set and row chrome specified in Layout & Entry Points §3 (Type pill · CVE/target mono · Scope label · Approver avatar+name · Granted relative date · Expires sla-pill · Revoke). |
| partial | grant-form (form) | ✅ covered | All four fields (scope target, approver, justification, expiry) are mandatory client-side gates on the submit button — there is no partial-submit state to design for (D-06). |
| partial | exceptions-list (list-collection) | ✅ covered (dismissed) | List is a single full-tenant fetch (mirrors `GET /campaigns`'s no-pagination-params precedent, Phase 38 D-04); there is no server-side partial-row-shape case distinct from the full-failure error state already covered above. |
| overflow | exceptions-list (list-collection) | ✅ covered | Scope-target names (long asset-group names, hostnames) truncate with ellipsis + native `title` tooltip in the Scope column, mirroring `TicketAssetCard`'s truncation-safety precedent; justification text is deliberately NOT shown in the compact row (only in the row's inline-expand), so it carries no table-cell overflow risk. |
| zero-one-many | exceptions-list (list-collection) | ✅ covered | Zero → empty state (above); one → single-row table, pagination footer suppressed (mirrors `Pagination` component's own zero/one-page guard); many → standard paginated table at the sitewide page size, sorted ascending by Expires by default. |
| long-text | grant-form (form) | 🧪 backstop | Justification textarea caps at 1000 characters with a counter appearing near the limit (mirrors `CommentInput`'s 9500-of-10000 warning pattern) — needs a held-out test asserting the counter renders and the textarea does not silently truncate mid-word before the cap. |
| long-text | exceptions-list (list-collection) | 🧪 backstop | Approver display name in the compact table cell truncates with ellipsis rather than wrapping and breaking row height — needs a held-out test with a long synthetic display name asserting row height stays constant. |
