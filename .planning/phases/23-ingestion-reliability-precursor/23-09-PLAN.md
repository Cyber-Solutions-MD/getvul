<interfaces>
connector-card.tsx today (23-RESEARCH Open Question 11): renders `<SyncStatusPill status={connector.last_sync_status} />` (L71) + last-sync-time + record count. It does NOT show last_error, next-sync, or failure count.

ConnectorConfig type (after Plan 06) carries: `last_sync_status: 'ok'|'syncing'|'failed'|null` (normalized), `last_sync_at: string|null`, `sync_interval_minutes: number`, `last_error: string|null`, `consecutive_failure_count: number`.

D-16 (last-error inline): show a one-line severity-colored summary ONLY when `last_sync_status === 'failed'`; expand-on-click or hover reveals the full `last_error` + `last_sync_at` timestamp. Healthy connectors render NO error line. Match the existing failed = `severity-critical` (red) convention SyncStatusPill uses (visual-language.md: a fully-failed sync is "down" not "degraded" — do NOT introduce amber here for a second convention).

D-17 (next-sync, frontend-derived, no backend): compute `nextSync = last_sync_at + sync_interval_minutes`; render "next sync in ~Xm" (or "~Xh"); if `last_sync_at` is null render "not synced yet"; if overdue render "sync due". Pure client math.

D-18 (failure count): when `consecutive_failure_count > 1`, render "failed N times in a row" near the error summary (a single failure is a blip — thresholding at >1 is reasonable; document the threshold in a comment).

Design system: JetBrains Mono for terminal-pasteable values (HTTP status codes / request-ids inside last_error); Inter for prose. Use `text-[var(--color-severity-critical-on-soft)]` where error text renders on a soft/tinted fill (visual-language.md Phase-20 rule). No freehand hex. copy-voice.md: terse, no "Oops"/"Please".

Frontend test: `cd frontend && npm run test -- connector-card`. connector-card.test.tsx was corrected in Plan 06 to real values + the new fields — extend it here, don't regress it.
