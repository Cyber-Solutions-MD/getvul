<objective>
Wire the provider-dispatch contracts (Plan 03) through every Asana-hardcoded ticketing call site — the three create paths, sync, close, the rule engine's two independent hardcodes, and the router's client-resolution helper — and add the tenant-scoped configured-providers endpoint (D-15). This fixes the live data-integrity bug where `provider:"JIRA"` silently creates the ticket in Asana while persisting `Ticket.provider="JIRA"`.

Purpose: REL-04 (create a Jira ticket) and REL-05 (GitHub create path) cannot work while `request.provider` is ignored for dispatch. This plan makes the provider string authoritative end-to-end.
Output: Provider-dispatched service/rule-engine/router + a new configured-providers endpoint + an integration test that proves each provider reaches its own client.
</objective>

| Tenant A ↔ Tenant B | Every connector-config + ticket lookup must stay scoped to the caller's tenant |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-23-09 | Elevation of Privilege | `_get_ticketing_client(provider)` connector lookup | mitigate | Preserve the existing `ConnectorConfig.tenant_id == user.tenant_id` filter exactly; never introduce a provider-only global lookup. Test asserts tenant B cannot resolve tenant A's connector |
| T-23-10 | Information Disclosure | new configured-providers endpoint | mitigate | Endpoint filters strictly by `user.tenant_id`; returns only provider names + enabled flag (no credentials, no secret_arn). Tenant-scoping regression test required |
| T-23-11 | Tampering (data integrity) | provider-vs-destination mismatch | mitigate | Task 1 makes `provider` authoritative for dispatch; test asserts the persisted `Ticket.provider` matches the client that actually created the external ticket |
| T-23-12 | Input Validation | user-supplied `provider` string | mitigate | Coerce through `TicketProvider(...)` enum (raises on unknown) before any lookup; the Pydantic regex `^(ASANA|JIRA|GITHUB)$` stays as the first gate |
