The SyncStatusPill bug (23-RESEARCH Open Question 11):
- backend never writes 'ok'/'syncing'/'failed'; sync.py writes "SUCCESS"/"FAILED" (uppercase). service.py::_to_response passes the raw value through unchanged.
- sync-status-pill.tsx: `type SyncStatus = 'ok'|'failed'|'syncing'|null`; `const key = status ?? '__never'`; `const {label,pillClass,dotClass} = STATUS_CONFIG[key]` → `STATUS_CONFIG["SUCCESS"]` is undefined → throws.
- Fix location (recommended): normalize in service.py::_to_response at the wire boundary ("SUCCESS"→"ok", "FAILED"→"failed", None→None), matching the existing CR-06 provider-lowercasing wire-convention precedent. Keep the frontend union as 'ok'|'failed'|'syncing'|null.
- Tests sync-status-pill.test.tsx + connector-card.test.tsx hardcode `last_sync_status:'ok' as const` — they must be corrected to exercise the real POST-NORMALIZATION contract AND a raw-backend-value guard so the bug can't silently return.

visual-language.md: SyncStatusPill `failed` uses `severity-critical` (red) today — a fully-failed sync is "down" not "degraded"; keep that. Do not introduce a second color convention.

Backend pytest form (per-file + env vars) — see Plan 01. Frontend: `cd frontend && npm run test -- <pattern>` (vitest).
