# Phase 25 — UI Design Contract

> Visual and interaction contract for "Asset-Aware Remediation Guidance." Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** This phase does not introduce a new screen. It adds ONE new dedicated section — **"Remediation guidance"** — to the existing vuln `DrillPanel`/`DrillContent` (`frontend/src/components/vulnerabilities/drill-content.tsx`, both desktop and mobile variants — mobile renders `DrillContent` directly, so one insertion covers both), plus a new **description textarea** inside the EXISTING ticket-create `ConfirmModal` (same file, `renderConfirm`/`ConfirmModal` branch). Every token, layout pattern, and state-shell below is inherited from `sketch-findings-getvul` and from **Phase 24's already-approved `24-UI-SPEC.md`** — this contract reuses Phase 24's AI section chrome + two-tier citation component **unchanged** (per CONTEXT D-06/D-07) and specifies only: (a) where the new section sits, (b) the two NEW typed states Phase 24 didn't have (honest insufficient-evidence-for-remediation vs. the safety-refusal card), and (c) the description-textarea pre-fill contract (AIR-02).

## Interaction Contract — "Remediation guidance" section

**Placement (Claude's discretion per CONTEXT D-06, resolved):** inserted immediately **after** the existing raw "Remediation" section (which shows the scanner's own `remediation`/`remediation_info` text unstyled, already shipped) and **before** "Activity":

```
Header → CVSS → Affected hosts → Description → AI Explanation (Phase 24) → Remediation (raw scanner text) → Remediation guidance (NEW) → Activity → Actions
```

Rationale: the analyst reads the raw vendor text first, then requests the OS/package-aware actionable interpretation of exactly that text — "cite before interpret" (D-03) is reinforced by the physical reading order, not just the citation tiers within the section. This is the ONE new placement decision this contract locks (everything else is D-06/D-07 inheritance).

**Section body states (mutually exclusive, one renders at a time — extends Phase 24's 8-state list with 2 new states, reusing the identical mechanism):**

1. Cache hit on mount → validated cited steps render immediately (identical `AiExplanationCitations` renderer, `resourceType='remediation'`) + the "Copy into ticket description" text-button beneath it + `AiFeedbackControl` (D-07 inherited, thumbs capture). No button ever shown.
2. Cache miss, key configured, role ≥ Analyst, deterministic gate (D-01) finds usable grounding → **"Get remediation guidance"** button.
3. Cache miss, key configured, role ≥ Analyst, deterministic gate (D-01) finds NO usable grounding → the **insufficient-evidence card renders immediately, no button ever shown, no model call spent** (this is the UI expression of D-01's "no model call is spent" — the client never offers an action that's already known to be unsatisfiable).
4. Cache miss, role = Viewer → muted "No remediation guidance generated yet." text — no button (D-17 inherited).
5. No key configured → the no-key-configured card (D-23 inherited verbatim), regardless of cache/role/grounding.
6. Button clicked → "Analyzing this finding…" progress state — **identical pulsing-dot component reused from Phase 24**, not a new copy variant (the noun stays "this finding," not "this fix," so the shared component needs zero prop change).
7. Model responds, schema-valid, `grounded=true`, denylist clean → replay into state 1's rendering (respects `prefers-reduced-motion` exactly as Phase 24).
8. Model responds but `grounded=false` (the model's OWN post-hoc judgment, D-02's second layer) → **same card as state 3** — the analyst never sees which of the two refuse-layers fired.
9. **Dangerous-pattern denylist hit (D-04)** → the **safety-refusal card** (danger/red, above). This is checked AFTER schema validation succeeds and BEFORE the response ever reaches the citation renderer — a partially-dangerous step set is never rendered, never streamed, never cached as retrievable content (the audit log retains the hit per D-04, the UI never does).
10. Anthropic 429/busy → provider-busy card (D-07/D-25 inherited).
11. Tenant budget exceeded → budget-exceeded card (D-07/D-06-Phase24 inherited).

**No new state vocabulary beyond states 3 and 9** — everything else is a direct, unmodified reuse of Phase 24's mechanism with `resourceType='remediation'` substituted.

## Interaction Contract — AIR-02 draft-ticket description pre-fill

Target: the EXISTING ticket-create `ConfirmModal` in `drill-content.tsx` (desktop) / the mobile `renderConfirm` equivalent — **the same dialog**, not a new one.

1. **Trigger:** the **"Copy into ticket description"** text-button appears only in section-state 1/7 above (a validated, grounded, denylist-clean cited-steps result exists). Clicking it stores the **plain-text-flattened** cited steps (citation tinting is a rendering-only concern; the copied text is the raw `summary`/steps string, not HTML) into local component state — it does **not** open the ticket-create dialog itself; the analyst still clicks "Create ticket" separately, exactly as today.
2. **The dialog gains one new field:** a `Textarea` (shadcn — new addition, see Registry Safety) between the existing `TicketProviderPicker` and the Confirm/Cancel action row. Label: the description-field caption above. The textarea is **pre-filled** if the analyst used the copy-in affordance in step 1; otherwise it starts **empty** (not every ticket flows through remediation guidance — D-09 fences this to description-only, no forced dependency).
3. **The analyst can freely edit or clear the textarea before clicking Confirm.** Nothing is submitted, mutated, or sent to Jira/Asana until the existing "Create ticket" confirm click — this satisfies AIR-02's "review/edit before creating" clause using the exact same human-click gate the dialog already enforces for provider selection.
4. **No character-count UI, no required-field validation** — an empty description is a valid ticket (matches the current schema, which has no description field requirement today); this field is purely additive.
5. **Scope fence (D-09, restated for the executor):** this textarea carries ONLY the remediation-guidance text the analyst chose to copy in. It does **not** pre-fill the ticket title, does **not** pull in asset context, and does **not** touch Jira/Asana field-mapping — those are explicitly Phase 27 (AID-01). If a future field appears in this dialog beyond description, it is out of this phase's scope by definition.
