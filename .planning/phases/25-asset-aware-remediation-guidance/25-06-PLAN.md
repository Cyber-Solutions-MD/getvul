<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → `POST /api/v1/tickets` body | Untrusted request body with a new free-text field crosses; must be bounded + not mass-assignable |
| `create_tickets()` → external ticketing provider | Analyst-authored text flows to Jira/Asana/GitHub as the ticket body |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-06 | Tampering | `TicketCreateRequest` | mitigate | `max_length=10000` + `extra="forbid"` + whitespace-coercion validator — the project's existing free-text-field defense (CommentCreate/BlockedUpdate precedent), ASVS V5 |
| T-25-07 | Elevation of Privilege | `create_new_tickets()` route (unchanged) | accept | The description rides the EXISTING authorized ticket-create endpoint — its current authz gate is reused verbatim; no new endpoint, no new role path introduced. Adding a description cannot let an unauthorized role create a ticket it could not already create |
| T-25-10 | Repudiation | `create_tickets()` notes override | accept | The analyst-authored body replaces the auto-built one by design (D-08/A3 WYSIWYG); the ticket audit trail already records ticket creation by the acting user — provenance of the body is the analyst's own reviewed text, which is the intended behavior |
</threat_model>
