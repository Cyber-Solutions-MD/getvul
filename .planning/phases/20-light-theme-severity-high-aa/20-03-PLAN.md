<false-green-guard>
This gate must be BOTH un-foolable (no false-green) AND satisfiable on a clean pass (no false-never-green).
A prior revision guarded on `grep -q "/dashboard/settings"` — but the spec only prints a route path when
an assertion FAILS or a violation is `console.error`-logged (confirmed against 19-04-SUMMARY.md, same
spec + `list` reporter). On a clean 0-violation pass NO route name is printed, so that guard could
NEVER match on success — a false-never-green. The correct, satisfiable mechanism:

1. PRIMARY, authoritative signal: `test "${PIPESTATUS[0]}" = "0"`. Playwright exits non-zero if ANY
   blocking describe fails, errors, times out, or the server is down. Exit 0 therefore means "the run
   completed and every blocking block passed (0 blocking violations)". This alone closes the original
   false-green hole. (Use `PIPESTATUS[0]`, NOT `;`-severed grep, so the `tee` pipe does not mask the code.)

2. Both-themes-ran proof: grep the `list` reporter's PASSING (✓) line for EACH blocking describe (dark +
   light). Both must appear, proving both themes ran and passed.

3. Reached-the-end proof: an UNCONDITIONAL end-of-loop `console.log` (added in Task 1) that always prints
   on a completed run — `[axe] light sweep completed: N routes, last=…` — with N and the last route
   pasted into the SUMMARY and cross-checked against STATIC_ROUTES.length + discovered detail routes.

DO NOT add a `! grep -qiE "\[(serious|critical)\]"` clause: the REPORT-ONLY WCAG 2.2 block
(`console.warn([${v.impact}] …)`, e.g. target-size) can legitimately log `[serious]`/`[critical]` strings
for NON-blocking violations on an otherwise-passing run — such a clause would reintroduce false-never-green.
`PIPESTATUS[0]=0` is the authoritative "0 BLOCKING violations" signal; rely on it.
</false-green-guard>
