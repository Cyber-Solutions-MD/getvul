<objective>
Replace the ad-hoc default-credential rejection on the forced-rotation endpoint
(`POST /auth/change-password` when `must_change_password` is set) with a real
password policy: configurable complexity, an active password-history check, and
a similarity/edit-distance guard that closes the `Admin1234!` near-variant gap
left as the documented WR-01 residual (Phase 06).

Purpose: Phase 06 WR-01 closed exact / whitespace / case variants and
current-password-hash reuse, but `DEFAULT_POLICY` has `history_count=0` and all
complexity flags `False`, so near-variants of the install credential still pass.
This phase raises the floor for the forced-rotation path only, without removing
tenant-policy configurability, and keeps every WR-01 guard intact.

Output: 3 new pure/typed functions + 1 constant in `password.py`, a policy
override param on `change_password()`, the similarity guard + strong-policy floor
wired into the flagged branch of the `/change-password` endpoint, and extended
tests in `test_admin_hardening.py` proving all four ROADMAP success criteria.

| Boundary | Description |
|----------|-------------|
| client → POST /auth/change-password | A flagged (first-login) user submits an attacker-chosen `new_password` and `current_password` across the network; both are untrusted input crossing into the auth/credential store. |
| forced-rotation gate → credential persistence | The must_change_password gate must hold: a rotation that succeeds writes a new bcrypt hash and clears the flag; a weak/near-default/recycled rotation must not be allowed to defeat it. |
