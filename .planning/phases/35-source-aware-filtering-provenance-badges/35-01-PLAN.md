`tuple_` (from sqlalchemy); `or_` and `VulnerabilityCorrelation` are already imported (PATTERNS §service):
```python
if filters.source:
    corr_subq = (
        select(VulnerabilityCorrelation.cve_id, VulnerabilityCorrelation.asset_id)
        .where(
            VulnerabilityCorrelation.tenant_id == tenant_id,
            VulnerabilityCorrelation.sources.contains(filters.source)
            if filters.source_mode == "and" and len(filters.source) >= 2
            else VulnerabilityCorrelation.sources.overlap(filters.source),
        )
    )
    if filters.source_mode == "and" and len(filters.source) >= 2:
        # AND: only rows with a qualifying correlation (single-source rows can't corroborate)
        query = query.where(tuple_(Vulnerability.cve_id, Vulnerability.asset_id).in_(corr_subq))
    else:
        # OR (default) / AND-with-<2 no-op: correlation overlap OR direct per-row source
        # (covers single-source findings that have NO correlation row at all — 35-RESEARCH §2)
        query = query.where(
            or_(
                tuple_(Vulnerability.cve_id, Vulnerability.asset_id).in_(corr_subq),
                Vulnerability.source.in_(filters.source),
            )
        )
```

flags this as an impl-detail risk); if the composite-IN-subquery form misbehaves, fall back to an EXISTS
correlated subquery with the same OR/AND branch semantics.

query_count.py harness (NEW, backend/tests/query_count.py) — no analog exists (PATTERNS §new infra). A
plain context manager, no fixture needed; attach to engine.sync_engine (asyncpg async-engine idiom):
```python
from contextlib import contextmanager
from sqlalchemy import event
from app.db.session import engine

@contextmanager
def count_queries():
    statements: list[str] = []
    def _listener(conn, cursor, statement, parameters, context, executemany):
        statements.append(statement)
    event.listen(engine.sync_engine, "before_cursor_execute", _listener)
    try:
        yield statements
    finally:
        event.remove(engine.sync_engine, "before_cursor_execute", _listener)
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → GET /vulnerabilities?source=&source_mode= | untrusted filter values cross into ARRAY `&&`/`@>` operators |
| primary paginated query → batched correlation query | the second (batched) query must independently enforce tenant scope |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-01 | Information Disclosure | page-scoped batched correlation fetch (`tuple_(...).in_(page_keys)`) | mitigate | Include `VulnerabilityCorrelation.tenant_id == tenant_id` explicitly on the SECOND query, not just the primary — matches the codebase's scope-both-queries convention (35-RESEARCH V4). test_summary_carries_sources runs single-tenant; add a cross-tenant seed guard if a second tenant fixture is available. |
| T-35-02 | Tampering | source_mode query param | mitigate | Pydantic `Literal["or","and"]` rejects any other value with 422 (test_bad_source_mode_422); source values already pass through the existing `Vulnerability.source.in_()`/ARRAY operators parameterized (no string interpolation). |
| T-35-03 | Denial of Service | ARRAY `&&`/`@>` on the GIN-indexed sources column | accept | `sources` is GIN-indexed (034); overlap/contains are index-scannable; `source` list is capped `max_length=10` (existing schema cap). Read-only, no unbounded fan-out. |
</threat_model>
