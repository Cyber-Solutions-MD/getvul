## Decisions Made

- **`custom_id_hash_map` typed `dict[str, str]`, not the bare `dict` RESEARCH/PATTERNS showed:** running `mypy app/ai/models.py` in isolation surfaced a genuine, NEW "Missing type arguments for generic type dict" error -- confirmed via `mypy-baseline.txt` inspection that `app/ai/models.py` had zero pre-existing baseline entries (unlike `app/audit.py`/`app/assets/models.py`, which already carry this exact baselined debt for their own `Mapped[dict]` columns). Rather than add a new baseline entry for a trivially avoidable case, the column was typed precisely (`dict[str, str]`, matching its real shape: a finding_id string mapped to a factor-hash string). `mypy app/ai/models.py` now reports zero issues.
- **`anthropic_batch_id` uniqueness via a standalone `op.create_index(..., unique=True)`, not an inline column/table constraint:** matches the plan's own literal migration action text. Confirmed this is DDL-equivalent to a `UNIQUE` constraint at the Postgres level (a unique index is how Postgres implements uniqueness either way) -- verified live via the `test_ai_batch_job_anthropic_id_unique` test, which raises `IntegrityError` on a duplicate.
- **No live top-N re-check in `_is_finding_queued()` (Assumption A3):** the helper answers only "is this finding in an already-submitted in_progress batch," never "will tonight's not-yet-submitted batch include it." A not-yet-submitted finding shows `queued: false` and gets the ordinary on-demand "Explain the priority" trigger -- arguably the better analyst experience (an immediate option, not a passive wait for something that hasn't started), and avoids re-running the D-01 top-N query on every single GET.
