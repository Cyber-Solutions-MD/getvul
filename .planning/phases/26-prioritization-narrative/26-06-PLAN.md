<objective>
Add the durable `AiBatchJob` Postgres registry (model + migration 033) and wire the backend `queued` boolean into the on-demand GET cache-check that Plan 04's frontend already consumes. This is the durability foundation the batch submitter (Plan 07) writes to and the poller (Plan 08) resumes from — a Message Batch can legitimately still be in_progress up to 24h later, spanning a restart, so an in-memory dict (like scheduler.py's `_running_syncs`) is provably insufficient (RESEARCH Pitfall 2).

Purpose: Deliver the smallest durable-state piece first (table + the read-side `queued` signal) so Plan 07's submit path has a row to INSERT and Plan 04's already-shipped queued card gets its live signal. No batch is submitted in this plan — the registry is created and read, not yet written by a real submission.
Output: the `AiBatchJob` model, migration 033, the `_is_finding_queued()` helper + `queued` GET field, and their tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Submitted batch state → process restart | Batch tracking must survive a restart; an in-memory dict orphans real spend |
| AiBatchJob row → GET queued signal | The queued signal must be tenant-scoped; tenant B's batch must never surface on tenant A's finding |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-08 | Denial of Service (orphaned spend) | `AiBatchJob` durability | mitigate | The registry is a Postgres row (unique `anthropic_batch_id`), not an in-memory dict — a batch that spans up to 24h + a restart is always re-findable by Plan 08's poller. Test asserts a durable round-trip in a fresh session. |
| T-26-03 | Information Disclosure (cross-tenant) | `_is_finding_queued()` / GET queued signal | mitigate | The queued query filters on `AiBatchJob.tenant_id == user.tenant_id` (never join-derived from the result payload); cross-tenant isolation test proves tenant B's batch never surfaces on tenant A's finding. |
| T-26-05 | Elevation of Privilege | GET route (queued added) | mitigate | The queued field rides on the existing `require_viewer` GET — no new endpoint, no new role surface; the helper adds only a read scoped to the caller's own tenant. |
</threat_model>
