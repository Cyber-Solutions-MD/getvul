  <decision>Approve the durable shape of the `alerting_guard` table and confirm migration 051 provisions the guard table + `Tenant.alerting_config` + `Tenant.alerting_last_digest_sent_at` in ONE migration before it is written. This is a one-way door (D-05 reversibility: a new Alembic table; dropping it loses alerted-history and reopens the double-fire window).</decision>
  <context>D-05 keys the guard `(tenant_id, cve_id, asset_id, trigger_type)`. Discretion items to lock now: (a) store `fired_at` timestamptz for observability vs. bare existence rows; (b) `trigger_type` as a bounded string `'kev' | 'epss'`; (c) persist the digest send marker as a Tenant column (`alerting_last_digest_sent_at`) vs. a separate table — recommended column, so restarts don't double-send (Pitfall 4). Recommended: dedicated `alerting_guard` table, `UniqueConstraint(tenant_id, cve_id, asset_id, trigger_type)`, nullable `fired_at`, indexed on `(tenant_id, trigger_type)` for the per-slice subtraction.</context>
  <options>
    <option id="option-a">
      <name>Recommended: dedicated alerting_guard table + fired_at + Tenant.alerting_last_digest_sent_at column</name>
      <pros>Clean identity match to (cve,asset,trigger); cheap observability; durable send marker survives restarts; single migration 051</pros>
      <cons>One-way — adds a table + two columns via Alembic</cons>
    </option>
    <option id="option-b">
      <name>Bare existence rows (no fired_at) + in-memory send marker</name>
      <pros>Slightly smaller table</pros>
      <cons>Loses observability; in-memory marker double-sends digests after every restart (Pitfall 4) — rejected by research A2</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or specify overrides (table name, columns, index)</resume-signal>
