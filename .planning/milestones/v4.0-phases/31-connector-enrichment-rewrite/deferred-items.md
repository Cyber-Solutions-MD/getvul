## 31-02-01: No test-mode gate — `settings.environment` defaults to `"production"`, so the real scheduler (and now the real EPSS/KEV feed fetch) starts during ANY `client`-fixture test

**Found during:** Plan 02 Task 3, wave-level regression sweep (`test_vulnerability_enrichment.py` unexpectedly failing with a real `UniqueViolationError` on `epss_scores_pkey`, traced back through the docker dev stack's `--reload` backend container's own logs).

**Issue:** `app/main.py`'s `lifespan()` calls `start_scheduler()` whenever `settings.environment in ("development", "production")` (`main.py:107-110`). `Settings.environment` defaults to `"production"` (`config.py:11`) and **nothing in `conftest.py` overrides it** — there is no `"test"` environment value or pytest-detection idiom (`PYTEST_CURRENT_TEST`, an env var, etc.) anywhere in `app/`. This means every test using the `client`/`client_factory` fixtures (which wrap `asgi_lifespan.LifespanManager`) starts the REAL in-process scheduler, including — as of this plan — the new `_dispatch_enrichment_refresh()` (ENRICH-05). Unlike every other scheduler dispatcher (ticket sync, SLA check — tenant-scoped and cleaned by `conftest.py`'s TRUNCATE list; AI batch prewarm — gated on a per-tenant BYOK key that doesn't exist in a test env, so it silently no-ops), the EPSS/KEV fetch is (a) unauthenticated and hits real public internet endpoints with no precondition that would make it a no-op in a test environment, and (b) writes to `epss_scores`/`cisa_kev`, which are deliberately global (D-11) and are **not** in `conftest.py`'s post-test TRUNCATE list.

**Observed impact (this session):** The docker-compose dev stack's `getvul-backend-1` container (`uvicorn --reload`) picked up each in-progress edit to `scheduler.py`/`enrichment_feeds.py`/the new test files, reloading and re-running `start_scheduler()` on every reload. This populated the shared dev Postgres's `epss_scores`/`cisa_kev` with ~355k/1.6k REAL rows mid-session (confirmed via `docker logs getvul-backend-1`: `enrichment_refresh_completed epss_rows=355094 kev_rows=1660 status=ok`), which collided with this plan's own `test_enrichment_feeds.py` seed rows AND Plan 01's pre-existing `test_vulnerability_enrichment.py` seed rows (both used real-CVE-range IDs like `CVE-2024-...`/`CVE-1999-...`).

**Fixed within this plan's scope:**
1. A genuine, separate concurrency bug this same investigation surfaced — **fixed, not deferred** (Rule 1): `start_scheduler()`'s eager call and `_scheduler_loop()`'s own first-tick inline call raced (both observed a cold `_last_enrichment_refresh is None` gate before either finished), producing two overlapping delete-then-insert swaps and a real `UniqueViolationError`. Fixed with `_enrichment_refresh_lock` (`asyncio.Lock`) in `scheduler.py`; proven by a new regression test (`test_dispatch_enrichment_refresh_concurrent_calls_do_not_race`).
2. Both broken test files' seed `cve_id` values changed to a pre-1999 year (`CVE-1990-...`) — the real CVE numbering scheme's floor is 1999, so this range can never collide with real feed data, regardless of whether the ref tables happen to be empty or fully populated when the test runs (`test_enrichment_feeds.py`, `test_vulnerability_enrichment.py`).
3. The shared dev Postgres's `epss_scores`/`cisa_kev` tables manually `TRUNCATE`d back to empty after verification (SQL-level cleanup, not a git operation).

**Why the BROADER gap is deferred (not fixed structurally):** Adding a real test-mode gate (e.g., a `conftest.py` fixture that monkeypatches `settings.environment`, or an explicit `TESTING`/`PYTEST_CURRENT_TEST` check in `main.py`'s lifespan, or dependency-injecting a fake scheduler for tests) is a cross-cutting architectural change to test infrastructure shared by every scheduler dispatcher (not just ENRICH-05's), matching the exact precedent already logged in `phases/28-eval-cost-observability-gate/deferred-items.md` item `28-02` ("Background AI batch-prewarm scheduler races the `client` fixture's per-test app lifespan" — same root cause, same conclusion: Rule 4 territory, out of a narrowly-scoped task). This plan's job is ENRICH-05's scheduler wiring, not a redesign of how the test harness detects "am I running under pytest."

**Suggested fix (future, optional):** A `conftest.py`-level `autouse` fixture (session- or test-scoped) that either (a) monkeypatches `settings.environment` to a value NOT in `("development", "production")` for the duration of `client`/`client_factory`-based tests, or (b) pre-seeds `scheduler_module._last_enrichment_refresh = datetime.now(UTC)` (and the equivalent AI-batch/ticket-sync sentinels) at session start so no dispatcher's cold-gate fires unconditionally during tests, mirroring the `28-02` suggested fix. Whichever approach is chosen should be applied to ALL scheduler dispatchers at once (ticket sync, SLA check, AI batch prewarm/poll, enrichment refresh), not just this one, since they share the identical underlying cause.
