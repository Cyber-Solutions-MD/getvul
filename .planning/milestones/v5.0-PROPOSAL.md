# Milestone v5.0 (PROPOSAL): Close the Loop — Remediation Orchestration & Assurance

**Status:** 📋 DRAFT / PROPOSED — not started. Formally activate via `/gsd-new-milestone` **after v4.0 ships** (do not run two active milestones).
**Proposed phases:** 36–45 (10 phases) — numbering provisional, finalized at activation (continues from the last v4.0 phase).
**Drafted:** 2026-08-10 (research-grounded; see Sources).
**Depends on:** v4.0 (Enriched Risk Exposure & Source-Aware Triage) complete — v5.0 consumes v4.0's deterministic, versioned risk-exposure score and source-aware provenance throughout.

## Why this milestone

GetVul's arc so far solved **seeing and deciding**: multi-scanner correlation (v1–v2), a BYOK AI copilot that explains/prioritizes/drafts (v3.0), and a real risk-exposure model with EPSS/KEV/native-signal enrichment and source-aware triage (v4.0).

2026 market research is consistent: **prioritization is largely a solved problem** (EPSS + KEV + exposure/reachability + SSVC) — and v4.0 builds most of it. The unmet need has moved **downstream to closing the loop**: routing a finding to the right owner, driving it to fixed under a risk-based SLA, *verifying* the fix, governing exceptions, and **proving the whole program to leadership**. RBVM maturity is now judged on **MTTR by risk tier and SLA compliance**, not scan volume; the recurring gaps cited are remediation orchestration, auto-close-on-rescan, exception/risk-acceptance, executive + compliance reporting, and integration/automation (API, webhooks, two-way ITSM).

v5.0 turns GetVul from "*see and decide*" into "*operationalize, close, and prove*" — without leaving its lane (a triage/ownership/orchestration layer on top of existing scanners; **not** a scanner or a patch-deployer).

**Product guardrails carried forward:** single-VM Docker Compose + in-process asyncio scheduler only (no new infra); every query tenant-scoped; audit events for all new mutating actions (SLA policy changes, exceptions/risk-acceptance, campaign actions, API writes); BYOK-only AI (tenant's own key, inert until configured); the deterministic risk-exposure score stays authoritative — v5.0 acts on it, never re-derives it.

## Proposed phases (10 features)

### Phase 36: Remediation SLA engine & escalation — `SLA-*`
Risk-tier SLA timers (e.g. critical 7d / high 30d / moderate 90d, tenant-configurable) computed off the v4.0 risk-exposure tier; breach-approaching and breach states; auto-escalation to Slack / Microsoft Teams / email / PagerDuty at configurable thresholds; MTTR captured per risk tier.
**Success criteria:** (1) each open finding shows a live SLA state derived from its risk tier + configurable policy; (2) approaching/breached transitions fire the configured escalation channel exactly once, audited; (3) MTTR-by-tier is queryable for reporting.
**Depends on:** v4.0 risk model. Extends today's severity-keyed SLA into a real engine.

### Phase 37: Two-way ticket sync & remediation verification — `SYNC-*`
Bi-directional status sync from Jira / Asana / GitHub (status write-back into GetVul, not just create); auto-close a finding when a subsequent scanner sync no longer reports it (rescan-confirmed fix) with a reopen guard.
**Success criteria:** (1) a ticket moved to Done in Jira reflects on the linked finding without manual action; (2) a finding absent from N consecutive post-fix syncs auto-closes with an audit trail; (3) a recurrence reopens rather than silently re-creating.
**Depends on:** existing ticketing connectors; closes the one-way gap.

### Phase 38: Remediation campaigns (bulk fix orchestration) — `CAMP-*`
Group findings by shared fix (CVE / patch / product) across many assets and owners into a campaign; bulk-create/assign tickets; track per-campaign progress and MTTR.
**Success criteria:** (1) an analyst launches a campaign from a CVE/fix group spanning multiple assets in one action; (2) campaign progress (open/in-progress/done, % remediated) is live; (3) campaign actions are audited and respect owner routing.
**Depends on:** existing cross-asset-by-CVE grouping + owner routing.

### Phase 39: Exception & risk-acceptance workflow — `EXC-*`
First-class mark-false-positive and accept-risk with required justification, approver, scope (finding / asset / asset-group), and mandatory expiry; suppressed items leave active queues but remain auditable and auto-resurface on expiry.
**Success criteria:** (1) an accepted-risk finding is excluded from active queues, SLA timers, and dashboards until expiry; (2) every exception records who/why/scope/expiry and emits an audit event; (3) expired exceptions automatically return to the active queue.
**Depends on:** extends existing "asset ignored" / exposure-override precedent.

### Phase 40: Proactive alerting & digests — `ALERT-*`
Event alerts when a *newly* KEV-listed or high-EPSS CVE affects the tenant's own assets; scheduled per-owner/per-team digests (Slack / Teams / email) of what's due, breaching, or newly critical.
**Success criteria:** (1) a new KEV/EPSS-threshold match on an owned asset fires a targeted alert; (2) scheduled digests deliver owner-scoped summaries on the in-process scheduler; (3) alert rules + delivery are tenant-configurable and audited.
**Depends on:** v4.0 enrichment feeds + existing notification primitives.

### Phase 41: Coverage & blind-spot detection — `COV-*`
Reconcile the authoritative asset inventory (IdP / MDM / HR / CMDB) against assets seen by scanners to surface unscanned/unmanaged hosts and per-connector coverage gaps.
**Success criteria:** (1) a "coverage" view lists inventory assets with zero scanner findings/last-seen; (2) per-connector coverage % and stale-source gaps are shown; (3) newly-discovered unmanaged assets can be routed to an owner.
**Depends on:** GetVul's existing IdP/MDM/HR asset data.

### Phase 42: Risk trend analytics & burndown — `TREND-*`
Historical risk-exposure over time, backlog aging, and per-team / per-asset-group burndown, built on v4.0's versioned score (version-boundary-aware so a model change doesn't corrupt trends).
**Success criteria:** (1) tenant/team/asset-group risk-exposure trend lines over a selectable window; (2) backlog aging (open findings by age × severity) and burndown rate; (3) trends annotate risk-model version boundaries rather than blending across them.
**Depends on:** v4.0 Phase 34 (historical recompute) for a clean score history.

### Phase 43: Executive & compliance reporting — `RPT-*`
Role-based dashboards + exportable board/exec report (PDF) covering risk trend, SLA compliance, MTTR by tier, and remediation progress; findings mapped to compliance frameworks (SOC 2, ISO 27001, PCI DSS, NIST CSF).
**Success criteria:** (1) an exec/board PDF exports with risk trend + MTTR + SLA-compliance for a selected period; (2) role-scoped dashboards (analyst / IT-ops / compliance / leadership) render tenant-scoped; (3) a compliance view groups findings by framework control.
**Depends on:** Phases 36 (MTTR/SLA) + 42 (trends).

### Phase 44: Natural-language query assistant (AINL-01) — `NLQ-*`
Ask questions over the tenant's own vuln/asset/ticket data in plain English ("which internet-facing hosts have an unremediated KEV older than 30 days?"), reusing the v3.0 BYOK AI scaffold and guardrails, translating to safe tenant-scoped queries (never free-form SQL).
**Success criteria:** (1) NL questions return grounded, tenant-scoped answers with the underlying result set shown; (2) queries are constrained to a safe schema (no injection, no cross-tenant reach); (3) inert until the tenant's own key is configured (BYOK guarantee).
**Depends on:** v3.0 AI scaffold. (This is the AINL-01 item deferred from v3.1.)

### Phase 45: Public API, webhooks & SDK — `API-*`
Documented, authenticated, tenant-scoped REST API (read + write for findings/tickets/exceptions/campaigns), event webhooks (finding created / SLA breached / ticket synced / exception granted), and a minimal client SDK for SOAR / ITSM / data-pipeline integration.
**Success criteria:** (1) API keys are tenant-scoped, RBAC-gated, rate-limited, and audited; (2) webhooks deliver signed events with retry; (3) an OpenAPI spec + SDK cover the core read/write surface.
**Depends on:** event surface from Phases 36–39; capstone platform layer.

## Considered but set aside (swap candidates)
- **SBOM / container / IaC scanning** and **attack-path / reachability graphs** — high value in the market but push GetVul toward *being* a scanner/graph engine; out of its "layer on top of scanners" lane and infra-heavy. Revisit as a separate track if positioning changes.
- **SSVC decision trees** — could substitute for Phase 42 if a formal decision framework is preferred over trend analytics; complements (doesn't replace) v4.0's deterministic score.
